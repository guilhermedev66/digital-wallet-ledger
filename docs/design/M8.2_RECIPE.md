# M8.2 structural recipe

Foundation: `docs/design/refero/brex-design.md` (real, verbatim). Supporting: the 4
adapted Spell components (`docs/design/spell/ADAPTATIONS.md`) and 3 Inspora
composition references (`docs/design/inspora-references.md`).

## What carries over from Brex, and what doesn't

Brex's DESIGN.md documents a **white-canvas, light-primary** marketing site. This
project's palette (near-black/graphite/warm-gray/off-white/amber) is explicitly
kept per the M8.2 brief ("color is secondary... palette can retain black,
graphite, warm gray, off-white, amber"). So Brex is adopted as **structural and
compositional discipline**, not a literal reskin:

**Adopted (structural, not visual):**
- "One accent for exactly one purpose per region" — enforced strictly across all
  5 screens below (this project already leans this way; Brex's Do/Don't list
  makes it a hard rule, not a preference)
- Flat surfaces, hairline borders, **zero drop shadows** for elevation — already
  this project's direction; Brex confirms and hardens it
- Section/card spacing rhythm — Brex's 48-80px section gap / 24-32px card padding
  maps directly onto this project's existing `--space-6`-`--space-8` tokens, no
  change needed
- Concrete component *patterns* per screen — see below, one per screen, quoting
  the actual Brex component it's adapted from

**Not adopted (kept from the existing, already-approved token system):**
- Brex's literal color values (white canvas, Ink/Fog/Mist) — superseded by this
  project's own near-black/graphite/amber tokens, per the brief
- Brex's radius system (6px/12px) and Inter+Flecha typography — the existing
  `tokens.css` sharp 1-2px radii + IBM Plex Sans/Mono is this project's
  already-validated "Ledger Terminal" identity (M8/M8.1's own token rewrite,
  independently QA'd twice already); the M8.2 brief's complaint was structure/
  hierarchy, not typeface or corner radius, so this isn't being reset without
  being asked

## Per-screen recipe

**DASHBOARD** → Brex's *Feature Category Card* pattern ("heading + body +
anchor image, subtle separation by spacing alone, no visible border") for the
currency-grouped sections; Brex's *Customer Logo Grid* discipline (banded
section, centered heading, uniform grid) informs a real summary-strip-as-band
treatment rather than a title+button row. Inspora "Interactive Cards" (#5,
already used) stays for the wallet tile's number-first hierarchy.

**WALLETS (WalletCard)** → Brex's *Feature Category Card* + *Email Capture
Input* (field+button horizontally paired with 4-8px gap) for the deposit
drawer. Spell `Badge` for currency identity where it reads better than a plain
chip; Spell `CopyButton` (already wired) for the wallet ID.

**TRANSFER** → Brex's *Email Capture Input* pairing pattern (field flush
against its action) for the amount+quick-chip row; Brex's *Cookie Consent
Dialog* 3-button row pattern (primary filled / outlined / text link) informs
the review step's action hierarchy. Inspora "Payment Links" (#1) and "Session
Progress and Recovery Timeline" (#3) stay for the vertical connector and step-
state visualization. Spell `PopButton` mechanic (already wired) stays on
confirm.

**ACTIVITY** → Brex's *Article/Resource Card* row rhythm (hairline separation,
no nested boxes) reinforced; Spell `Badge` (already wired) for type/direction
tags, per Brex's single-accent Do/Don't (routine facts stay neutral).

**RECONCILIATION** → Brex's core sentence made literal: *"a precision
instrument for finance teams, not a marketing site"* — the health readout
should look like an instrument panel, not a banner. Brex's flat-surface,
zero-shadow, single-accent-reserved-for-attention discipline is the whole
design language for this screen.

## Constraints for every screen (repeat of standing rules, restated for this pass)

- Real data only, no fake metrics
- Hierarchy must hold in grayscale (no color-only differentiation)
- No visual gimmicks (no 3D tilt, no particle effects)
- Preserve all existing functionality: auth, wallets, currencies, funding,
  transfers, idempotency, activity, reversal, reconciliation
- Use existing `tokens.css` custom properties only — no new hex colors
- Reuse existing shared components (`Button`, `FlowButton`, `LabelInput`,
  `Field`, `Badge`, `CopyButton`, `PopButton`, `Kbd`, `EmptyState`, `ErrorBanner`,
  `Skeleton`) before writing new ones
